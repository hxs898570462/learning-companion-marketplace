# Lab 课程实践

目标是完成课程实践并理解老师要求观察和回答的内容。先读取 [共享学习协议](references/learning-protocol.md)。默认用户动手，智能体提供提示和基于反馈的分析；不一次生成整份实验答案。

## 建立实验要求

阅读讲解材料、任务说明、起始代码、数据结构和环境要求。先查看文件与配置再建议安装或改动。识别必做、选做、提交内容和明确问题，建立要求对照表，每项保留出处；推测的学习目标单独标注，不能变成老师要求。

用 [实验记录模板](assets/lab-notes-template.md) 记录要求、操作、观察点、证据和状态。无法读取的材料、缺失数据或无法运行的环境应具体说明，继续处理可确认部分。

优先沿用课程规定的数据、方法和指标。替代方案只有在必要时提出，并说明与原实验的差异；不要悄悄重写课程目标或替换整个 starter code。

## 实践循环

1. 选择当前依赖已满足的小任务，说明讲义要求、关联知识编号、目的及完成标准。
2. 在有助于理解时让用户先预测结果，给足够动手的提示。指定需要反馈的最少证据，例如改动片段、数值、图表或完整报错；不给尚未尝试任务的完整答案。
3. 等待反馈。将用户输出、AI 自行检查结果和预期结果区分。核对输入、环境与操作，定位是概念、实现、数据还是环境问题，给最小必要修正并让用户再次验证。
4. 结果可信后，结合讲义解释现象、条件与异常，帮助用户形成基于证据的回答。关键节点用参数变化、边界输入或解释问题检查迁移，不要求每步测验。
5. 更新要求表和进度，再推进下一步。用户明确要求代跑或完整示范时可以执行，但标注 AI 示范而不是用户完成。

## AI／数学实验的证据

按任务选择检查：张量形状、数据类型、随机种子、训练／验证／测试边界、损失与评价指标、梯度或数值误差、参数变化、收敛趋势等。避免为简单实验强加完整工程规范。

调试解释“为什么检查这里，以及结果能排除什么”，保留关键失败与修正。结果与理论不符时先核对条件和实现，不编造实验结论；未运行项保持待验证。

## 完成与联动

逐项核对必做任务、讲义问题和提交格式，分别标注已完成、待用户反馈、阻塞和选做未完成。给最终 Markdown 记录和实际代码／图表位置，不能只交最终数值。

遇到理论缺口短暂补讲并记录返回步骤；理论有歧义时回查讲义和理论笔记。进一步的小项目作为可选迁移方向，用户要做时再进入 Project 流程，不扩展必交实验。
